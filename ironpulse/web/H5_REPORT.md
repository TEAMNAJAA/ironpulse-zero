## 2. M1 — คะแนนตรงกับ H4 ทุกบิต

ตรวจสองชั้นด้วย `python h4\verify_webapp.py`

```
IMG_8436  3g       max |diff| = 0.000e+00   MATCH
IMG_8444  under3g  max |diff| = 0.000e+00   MATCH
```

**ชั้น B · เส้นทางโมเดล** สร้าง baseline ด้วย `web.baseline.build` จากชุดฝึกของ fold S2 seed 42
แล้วให้คะแนนคลิปเดียวกับที่ H4 ให้คะแนนใน fold นั้น

```
threshold  web 0.5822678967   h4 0.5822679000   ต่าง 3.3e-09
คะแนน 29 คลิป              ต่างมากสุด 4.977e-09
```

`raw_scores.csv` เก็บทศนิยม 8 ตำแหน่ง ความต่างระดับ 5e-09 จึงคือการปัดเศษของไฟล์เอง ไม่ใช่ความต่างของการคำนวณ

### ⚠️ ระหว่างทำข้อนี้เจอบั๊กจริงหนึ่งตัว
รอบแรกชั้น A ต่างกัน 3.1e-04 สาเหตุคือ `h4/extract_tracks.py` เก็บ track เป็น **float32**
ที่พิกัดราว 1000 px float32 ให้ความละเอียดเพียง ~6e-5 px เทียบกับสัญญาณของคลิปปกติที่ 0.042 px
จึงเป็นการสูญเสียความละเอียดโดยไม่จำเป็น **แก้เป็น float64 แล้วรันโซ่ H4 ใหม่ทั้งหมด**
ตัวเลข H4 ขยับเล็กน้อยเท่านั้น (AUC ราย fold 0.9413 → 0.9415) ข้อสรุปไม่เปลี่ยน และตอนนี้ตรงกันทุกบิต

## 6. ⚠️ สิ่งที่เพิ่มเข้ามาเพราะจำเป็น และเหตุผล

### 6.1 การหามาร์กเกอร์ใหม่อัตโนมัติในทุกคลิป
เว็บแอปเก็บตำแหน่งมาร์กเกอร์ชุดเดียวต่อเครื่อง แต่ชุด `Arise H4` ถ่ายคนละรอบและกล้องขยับไปราว 70 px
พอใช้ตำแหน่งเดิมกับคลิป fault มาร์กเกอร์จึงเกาะผิดจุด **A1 ของ IMG_8447 เพี้ยนจาก 22.2 เป็น 32.1 µm**

แก้ด้วย `markers.reacquire_all()` ที่หาลายตารางหมากรุกในรัศมี `tracking.reacquire_radius_px`
รอบตำแหน่งที่ผู้ใช้คลิกไว้ ก่อนเริ่มติดตาม เป็นวิธีเดียวกับที่ H4 ใช้ ผลจึงตรงกับ H4 ทุกบิต
ถ้าหาไม่เจอตามเกณฑ์ `reacquire_min_response` จะใช้ตำแหน่งที่คลิกไว้เดิมแล้วเตือน
ถ้าเจอแต่ขยับไปไกล จะเตือนว่ากล้องถูกย้ายและสเกลอาจเปลี่ยน

ค่าใหม่ทั้งสามอยู่ใน config ไม่มี hardcode

### 6.2 ปุ่ม "ตั้งมาร์กเกอร์ใหม่ 30 วินาที"
ทำได้จริงในไม่กี่วินาที เพราะเป็นการ**ตั้งตำแหน่งมาร์กเกอร์ใหม่** ไม่ใช่การสร้าง baseline ใหม่
**การสร้าง baseline ใหม่ให้เสร็จใน 30 วินาทีเป็นไปไม่ได้** เพราะ `min_baseline_clips` = 20
และคลิปละราว 7 วินาที รวมอย่างน้อย 140 วินาที
หน้าจอเขียนกำกับไว้ตรง ๆ ว่าปุ่มนี้ทำอะไรและไม่ได้ทำอะไร

## 7. ⚠️ ข้อจำกัดที่รู้ตัว

### 7.1 การยึด f0 กับ baseline อาจล็อกพลาดไปหนึ่ง bin
`analysis.use_baseline_f0` เปิดอยู่ ระบบจะหาพีคความเร็วรอบในช่วง baseline × (1 ± 5%) ก่อน
คลิป 3 กรัมหมุนที่ 18.12 Hz ส่วน baseline อยู่ที่ 19.08 Hz ขอบล่างของหน้าต่างคือ 18.126 Hz
**18.12 จึงหลุดออกไปนอกหน้าต่างหวุดหวิด** ระบบเลยล็อกที่ 18.24 Hz ซึ่งห่างไปหนึ่ง bin (0.12 Hz คือ 0.66%)

ผลกระทบจริงในเคสนี้เป็นศูนย์ เพราะ `order_tolerance` = 0.08 กว้างพอให้ A1 ยังวัดที่พีคจริง
(A1 = 946.26 µm ตรงกับ H4 เป๊ะ) และคะแนนกับคำตัดสินถูกต้อง **แต่ค่า f0 ที่แสดงบนหน้าจอคลาดไปหนึ่ง bin**

ทางแก้ที่เสนอ เลือกอย่างใดอย่างหนึ่ง ต้องให้ผู้ใช้ตัดสิน
(ก) ขยายหน้าต่างเป็น `max(f0_shift_warn, 3 bins)` (ข) ถ้าพีคในย่านกว้างเด่นกว่าพีคในหน้าต่างมาก ให้เลือกพีคย่านกว้างแล้วเตือน
(ค) ปิด `use_baseline_f0` แล้วยอมรับความเสี่ยงของบั๊ก K แทน

### 7.2 baseline ปัจจุบันสืบทอดปัญหาการเก็บข้อมูลของ H4
`seed_demo.py` สร้าง baseline จากคลิปปกติ 38 คลิป ซึ่ง 26 คลิปมาจากรอบถ่ายเดียว
แอปเตือนข้อนี้เองตอนสร้างเสร็จ ตามบทเรียนข้อ 7.9 ของ STATE
ตัวเลขที่ได้จากแอปจึงมีข้อจำกัดเดียวกับ H4 ไม่ใช่ปัญหาของแอป

### 7.3 คลิปปกติหลายไฟล์ขึ้นคำเตือน "A1 ต่ำกว่าพื้นการวัด"
เป็นพฤติกรรมที่ถูกต้อง เครื่องที่ปกติจริงจะสั่นที่ 16 µm ซึ่งต่ำกว่าพื้นการวัด 19.5 µm ของการจัดเฟรมชุดนี้
คำเตือนนี้บอกว่า **ค่าตัวเลขที่แสดงเชื่อถือได้น้อย** ไม่ได้บอกว่าเครื่องผิดปกติ
ถ้าซูมเข้าให้ µm/px ลดลงครึ่งหนึ่ง คำเตือนนี้จะหายไปเอง
